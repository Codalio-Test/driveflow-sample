# Implementation Plan: DriveFlow — Vehicle Rental Management Platform

## Summary

DriveFlow is a unified vehicle-rental management platform for independent rental agencies: a
public booking engine, a tablet-optimized photo-verified inspection workflow, counter check-out /
return / settlement, Stripe deposit pre-authorization and capture, fleet + maintenance
administration, and executive analytics. The backend is Rhino v4 on Rails (blueprint-first,
tenant-scoped by organization, Bearer `api_token` auth); the client is a rhino-react + Vite SPA
shipping the already-approved UI prototype verbatim (30 flat routes).

## PRD gaps compensated

One bullet per gap code in `.codalio/prd-integrity-report.json`:

- **FLOW_JOURNEY_MISMATCH** (high) — Elena's journey says "30-minute grace / $75/hr" but key_features,
  the overdue stories and the prototype all specify a 60-minute grace and an hourly fee capped at
  the daily rate. Plan normalizes to **60-minute grace** everywhere; the late fee comes from
  `VehicleCategory.late_hourly_fee` capped at the daily rate. Extra AC + `RentalSettlementCalculator`.
- **DATA_MODEL_UX_MISMATCH** (high) — booking protection tiers / add-ons were unpersisted. Added
  `Rental.protection_tier` (blueprint `server/.rhino/blueprints/rentals.yaml`) and persist tier +
  add-ons as `RentalCharge` rows (`insurance_protection` / `equipment_addon`). Extra AC.
- **DATA_MODEL_UX_MISMATCH** (high) — guest checkout had no representation. Made
  `CustomerProfile.user_id` nullable and added `full_name` / `email` so a guest profile can exist.
  Extra AC + public booking endpoint.
- **DATA_MODEL_UX_MISMATCH** (high) — open public `/signup` conflicts with Rhino's invitation-token
  registration. Plan adds a custom customer registration + email-verification Extra; staff
  onboarding keeps Rhino invitations. Extra AC.
- **DATA_MODEL_UX_MISMATCH** (medium) — `sample_data` carries Devise columns that do not exist in
  Rhino v4 auth. Use Bearer `api_token`/bcrypt; added `users.approved` boolean via a DriveFlow
  extension migration to back the "approved" data-model AC.
- **DATA_MODEL_UX_MISMATCH** (medium) — Vehicle status vocabulary conflict. Normalized enum
  `available|reserved|rented|maintenance|cleaning|overdue`. Extra AC.
- **DATA_MODEL_UX_MISMATCH** (medium) — Rental status vocabulary conflict. Normalized enum
  `reserved|confirmed|active|overdue|completed|cancelled`. Extra AC.
- **SITEMAP_PAGE_NO_AC** (high) — `/account/profile` had no story/AC. Added compensation ACs +
  handoff entry + `AccountProfilePage.tsx`.
- **PROTECTED_ROUTE_NO_AUTH_AC** (medium) — `/account/profile` missing from the redirect AC.
  Extended the authenticated guard to every `/account/*` route + compensated AC.
- **SITEMAP_PAGE_NO_AC** (low) — parent hubs `/booking`, `/counter`, `/admin` had no AC.
  Compensated ACs added for each hub's landing content.
- **PRD_PROTOTYPE_ROUTE_GAP** (low) — nav-only destinations (How It Works, Support, admin System
  items) have no sitemap route/AC. Treated as documented out-of-scope stubs — no route planned.

## Extras (NOT covered by blueprint — develop implements these by hand)

1. **Stripe deposit lifecycle** (`Payment`/`Rental#create`) — pre-auth hold, atomic capture+release, expand hold, charge-balance, refunds; webhook reconciliation. `server/app/services/stripe_payment_service.rb`, `server/app/controllers/api/payments_controller.rb`, `server/app/controllers/api/webhooks_controller.rb`. AC: capture/release/expand/charge extras.
2. **Surcharge & late-fee engine** (`Rental#update`, `RentalCharge#create`) — 60-min grace, refueling at premium per-gallon (default $8.00) from tank capacity × fuel variance, excess mileage × rate, hourly late fee capped at daily rate. `server/app/services/rental_settlement_calculator.rb`. AC: extras + AC-16-story rows.
3. **PDF generation** — rental agreement, itemized receipts, invoices. `server/app/services/contract_pdf_service.rb`, `server/app/services/receipt_pdf_service.rb` (prawn). AC: PDF extras.
4. **Photo/document uploads** — 4-quadrant inspection photos, damage close-ups, driver license, registration docs, signature image. ActiveStorage + `server/app/controllers/api/documents_controller.rb` with content-type whitelists. AC: upload extras + AC-2/AC-7/AC-10/AC-11 upload rows.
5. **Overdue sweeper** — scheduled job flips `Rental.status → overdue` after the 60-minute grace and raises alerts. `server/app/jobs/rental_overdue_sweeper_job.rb`. AC: AC-14 grace row.
6. **Notifications** — voucher, return-urgency SMS/email, receipts. `server/app/services/notification_service.rb`, `server/app/mailers/*`. AC: AC-2 voucher, AC-15 urgency notice.
7. **Analytics aggregates** (tenant-safe custom controller using `Rhino.query` only) — utilization %, RevPAC, deposit reconciliation, maintenance spend. `server/app/controllers/api/analytics_controller.rb`. AC: AC-13 rows.
8. **Fleet schedule matrix endpoint** — vehicle availability blocks per day. `server/app/controllers/api/fleet_controller.rb`. AC: AC-10 matrix row.
9. **Counter queue endpoints** — departures / returns with prep-readiness and grace flags. `server/app/controllers/api/counter_controller.rb`. AC: AC-4, AC-16 lookup rows.
10. **Public guest booking + availability search** — date range + location, no account required. `server/app/controllers/api/bookings_controller.rb` in a `:public` route group. AC: AC-1/AC-3/AC-5 guest rows.
11. **Customer self-registration + email verification** — Rhino v4 registration is invitation-token based, so open `/signup` is custom. `server/app/controllers/api/registrations_controller.rb`, `server/app/mailers/verification_mailer.rb`. AC: registration gap compensation row.
12. **Row-level scopes** — customers only see their own rentals/payments/profile. `server/app/models/scopes/rental_scope.rb`, `payment_scope.rb`, `customer_profile_scope.rb`. AC: AC-5 "only customer" row + tenant-isolation tests.
13. **QR code generation** — voucher/receipt QR (`rqrcode`), `qr_code_url` computed attribute on `Rental`. AC: AC-3 confirmation row.
14. **Odometer service triggers** — `service_due` / `next_service_odometer` computed attributes + `VehicleServiceDueScope`. AC: AC-12 rows.
15. **Prototype-aligned serialization (virtual attributes)** — the approved JSX reads display keys that are
   not columns. Each must be emitted by the controller/serializer via `rhino_computed_attributes`:
   Vehicles/AdminFleet `name` (`"#{year} #{make} #{model}"`), `plate` (=`license_plate`), `location`
   (=`location.name`), `miles` (formatted `current_odometer`), `health` (service-life %);
   Rentals queues `customer` (=`customer_profile.full_name`), `vehicle` (`"#{make} #{model} · #{license_plate}"`),
   `due`/`time` (formatted `scheduled_return_datetime`), `accrued`/`balance` (computed late fee);
   Payments `rental` (=`reservation_number`), `type`, `amount`, `status`;
   Inspections `departure`/`return` blocks and photo metadata. Develop implements these as computed
   attributes so the prototype's `data_contract` keys resolve. AC: every list/detail AC.
16. **Prototype-aligned grouped/aggregate endpoints** — the AdminFleetMatrix timeline (`api.get('/fleet_matrix')`),
   the Counter queue cards, and the Analytics KPIs/charts return grouped shapes defined in
   `.codalio/ui-handoff.json` `data_contract`; build them in `api/fleet#matrix`, `api/counter#departures|returns`
   and `api/analytics#show` using `Rhino.query` only.

### Cross-resource ownership / conditional rules (Extras)
- **Customer scope**: `Rental`, `Payment`, `CustomerProfile`, `Inspection` index/show for role `customer` are row-filtered to the requester's own `customer_profile` — via `Scopes::*Scope`, not blueprint YAML.
- **Counter gate**: deposit hold / release / capture require `Payment` store **and** `Rental` update — checked in the controller (`authorize_deposit!`).
- **Availability**: a vehicle is bookable only when `status == 'available'` and has no overlapping `Rental` in `reserved|confirmed|active`.
- **Maintenance gate**: an active `VehicleMaintenanceLog` forces `Vehicle.status = 'maintenance'` and removes the vehicle from online availability.

## Functional gaps (PRD functions with no prototype control)

These PRD-required functions are not present as controls in the approved prototype; ui-integration
scaffolds them **in the user's design idiom** (step 6) rather than dropping them:

- **Driver-license image upload at `/booking/checkout`** (AC-14-story) — prototype shows renter
  details + card only. Scaffold an upload control with preview next to the existing card block.
- **Vehicle registration document upload at `/admin/fleet/new`** (AC-10) — prototype has no upload
  field. Scaffold a document upload row in the existing form grid.
- **`/vehicles` availability results grid** — the prototype's `Vehicles` page renders filters + an
  alert but no result cards. Develop builds the grid from `useModelIndex('vehicle_categories')` so
  the approved filter/search chrome has data beneath it.
- **Stripe Elements card widget at `/booking/checkout`** — the prototype ships plain inputs.
  Develop swaps the input block for the Stripe Elements mount point (same layout).

## Access tiers & role routing

| Tier | Routes | Behaviour |
| --- | --- | --- |
| Public | `/`, `/vehicles`, `/booking*`, `/signup`, `/login` | anonymous allowed; landing lives outside the guard |
| Authenticated (customer) | `/account/*` | guard → `/login` when unauthenticated; wrong role → `/account/dashboard` |
| Authenticated (counter_agent, fleet_manager) | `/counter/*`, `/inspections/*` | wrong role → `/counter/departures` |
| Authenticated (fleet_manager) | `/admin/*` | wrong role → `/admin/fleet/matrix` |

Post-login landing: `customer` → `/account/dashboard`; `counter_agent` → `/counter/departures`;
`fleet_manager` → `/admin/fleet/matrix`. Each role owns at least one route group (no dead-end role).

## Implementation order (recommended stage flow)

Aligned with `--pipeline` and the PRD phases:

1. **Plan** — this artifact set (YAMLs, plan, criteria, index, handoff).
2. **Develop** — phase A: `bundle exec rails rhino:blueprint` + migrations (11 models) + seeds
   (roles, demo UsersRole per role, org, locations, categories, vehicles, rates, rentals).
   Phase B: implement **Extras** (services, custom controllers, jobs, mailers, ActiveStorage).
   Phase C: author backend unit + integration tests for every AC.
   Phase D: create the 30 page files at the handoff routes pre-wired with rhino-react hooks.
3. **UI / UI-Integration** — vendor the approved prototype JSX into the page files and wire data
   via the contracts in `.codalio/ui-handoff.json`; scaffold the functional-gap controls.
4. **Test** — `bundle exec rails test` + client build; tighten anything broken.
5. **Review** — PRD compliance + coverage report.

Phase sequencing follows the PRD: **Phase 1** (booking engine, inspections, check-out/agreement,
check-in/settlement) → **Phase 2** (fleet matrix, active rentals, overdue) → **Phase 3**
(payments/pricing, analytics/maintenance).
